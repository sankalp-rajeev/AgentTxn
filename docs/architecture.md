# Architecture and module ownership

Status: scaffold only. Follow PRD sections 9-16 and 30-36 when implementing.

## Runtime boundary

The agent proposes a tool call. An adapter creates an effect intent. The runtime
registers it in the ledger, constructs a certification view, evaluates executable
invariants, and produces a deterministic decision before external execution.

- `runtime/coordinator.py`: orchestrates the protocol.
- `runtime/certifier.py`: evaluates committed effects, active intents, unresolved
  effects, dependencies, external state, and contract capabilities.
- `runtime/scheduler.py`: waits and wakes dependent work without globally
  serializing independent operations.
- `runtime/reconciliation.py`: probes provider truth for ambiguous effects.
- `runtime/recovery.py`: handles compensation and escalation.
- `effects/`: owns typed intents, certainty states, graph edges, and persistence.
- `contracts/`: owns capability metadata and its validation.
- `invariants/`: owns developer-authored rules and their deterministic evaluation.
- `faults/`: owns seeded fault schedules rather than nondeterministic wall-clock races.
- `adapters/`: starts with direct tool calls; LangGraph is optional and deferred.
- `metrics/`: measures correctness, concurrency, recovery, cost, and runtime overhead.

The ledger is backed by PostgreSQL. Planned tables are transactions,
effect_intents, effect_observations, effect_dependencies, effect_events,
tool_contracts, scenario_runs, and benchmark_results. Add migrations before
persisting runtime state; none are generated by this scaffold.

## Benchmark boundary

`services/` models provider behavior, including the true outcome of effects.
`txnagentbench/` owns scenario loading, orchestration, and evaluation.
The evaluator must assess provider truth independently of the runtime's local
observations. `baselines/` must use the same scenarios and fault schedules.
`experiments/` owns comparisons, ablations, and reproducibility records.

Begin with Payments and Shipping, then add the refund/account-credit example
required to prove a conflict over disjoint resources. Identity is the second
required domain. CloudOps, research-inspired baselines, and LangGraph are deferred.

## Semantics to preserve

- Effect certainty: NOT_STARTED, PENDING, CONFIRMED, FAILED, UNKNOWN, COMPENSATED.
- Transaction status: ACTIVE, WAITING, RECONCILING, COMMITTED, COMPENSATING,
  ABORTED, NEEDS_REVIEW.
- Certification: COMMIT, WAIT, RECONCILE, COMPENSATE, REPLAN, BLOCK, HUMAN_REVIEW.
- UNKNOWN must never be collapsed into failure or success without evidence.
- Hard invariants include active intents and unresolved effects.
- Safe retries depend on declared provider capabilities.
- Compensation is a new effect and may fail; it is not rollback.
- Independent work must be allowed to proceed concurrently.

PRD section 15 shows an intermediate COMPENSATING effect state, while section 9.3
does not include it in the effect certainty enum. Resolve this distinction when
implementing the state machine, for example by tracking compensation progress
separately from certainty. The scaffold does not silently add a seventh state.

## Implementation gate

Before runtime implementation, complete the novelty check. Then implement only
the feasibility spike until its disjoint-resource failure and prevention are
demonstrated. Do not interpret placeholder modules as evidence that gates passed.
